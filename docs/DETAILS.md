# TokenCat in detail

Back to the [README](../README.md)

A small macOS menu bar app that shows system metrics alongside the sessions, output tokens, measured speeds and usage limits of your coding agents (Codex, Claude Code, OpenCode, Gemini CLI, Qwen Code, Copilot CLI, Amp, Cline, Roo Code and Kilo Code, omp and Pi, Factory Droid, Cursor, Grok, Hermes, OpenClaw, Goose and Kimi Code). It requires macOS 13 or later and uses only Swift, AppKit and SwiftUI. It uses no images or code from RunCat. The Windows version is covered in [Windows](#windows).

This is a reference that lists every rule for how the screens, collection and measurements behave. The introduction and previews are in the [README](../README.md). Run all commands below from the repository root.

## Running

```sh
./build.sh
open dist/TokenCat.app
```

If TokenCat is already running, a second launch opens the existing app's dashboard and exits. Opening the app again opens the Settings window. Installing from a release and allowing it through Gatekeeper the first time are covered in [README › Install](../README.md#install).

## Screens

### Dashboard

Click the menu bar item to open the dashboard as a popover; closing it with Esc or another click on the item returns focus to the previous app. Choosing `Detach as Panel` from the header's ⋯ menu (or ⌥ `Open as Panel` in the quick menu) opens it as a resizable panel (420 pt wide, at least 510 pt tall) that remembers its position and size, and if it was open when TokenCat quit, it reopens on the next launch without stealing focus. The screen shares five type sizes, semantic color tokens, one set of state glyphs and a 4 pt grid with the menu bar. Each fact lives in one place only: the header tells the state, the limits card the limits, the output card the records, the rows the sessions, and the bottom collection problems. The one exception is `Speed now` in the output card, which repeats one session's latest measurement as is and never combines it.

- **Header**: a pixel cat head and a status sentence (`2 sessions need input · 1 working`, `1 session working · 1 tool`, `1 session waiting for log · no record for 3m`, `No active sessions`). Priority is input needed > API retry > tool and working > waiting for log. The head changes its expression with the state. The gear opens Settings (⌘,), and the ⋯ menu has Detach as Panel (popover only), Settings… (⌘,), Activity Monitor, About TokenCat and Quit TokenCat (⌘Q). Shortcuts to the telemetry settings are on the telemetry warning button at the bottom and on the first-launch card.
- **Usage limits**: in their own card right under the header, one line per limit window when there's a value, named provider first (`Codex · weekly 28% used`, `Claude · 5-hour 42% used`), with the time until reset and how fresh it is: a [live check](#live-usage-limits) up to 2 minutes old reads `… · live`, and older values give the age of the record (`… · recorded 5m ago`), naming omp or Pi when they recorded it (`… · omp recorded 4m ago`). It isn't a forecast of when you'll run out. 85% or more is orange, 95% or more is red, values more than 10 minutes old are drawn faded, and after the reset time it shows `—` and `Reset · waiting for a … record` for a day, then hides. For Codex it's the live check or the value recorded in the logs; for Claude it's the live check, the value received through the [status line bridge](#claude-usage-limits-and-the-status-line-bridge) or the Claude desktop app's usage history; for both, also [omp's and Pi's usage history](#omp-and-pi-usage-history). Of the windows that haven't reset, the one with higher usage (the longer one on a tie) comes first, and the other one, when its reset time is known, gets its own line right under it (`Claude · weekly 31% used · Resets in 3d 4h`). The record age is measured from when TokenCat received a live or bridge value, or from the record time of the desktop app's, omp's or Pi's history. Reset times are never made up: the desktop app's history has none, and a live answer may have none, so then only the age (`Recorded 5m ago`) or `Live` is shown, without the time left. The row is named `Claude` because the limit belongs to the Claude account.
- **Output tokens**: the number of output tokens recorded in the logs over the last 5 minutes, with the total on the card's title line and 5-second bars under it. The bars are amounts recorded and are never converted into a speed. The scale is picked from {1, 1.5, 2, 3, 4, 5, 6, 8}×10ⁿ so the tallest bar fills at least 2/3, with minute ticks, and is given in the chart's help. When more than one client records, the total is split beside the title, largest first, as in `Claude Code 6.6k · Codex 1.2k`; clients that don't fit fold into `+N more`, down to the largest alone, then the split goes. The line under the title shows the increase and time of the last record, and from 30 seconds after the last record it gives the reason for waiting (API retry, a tool category such as `Running command`, working, waiting for log), beside the record when both fit. A session waiting for input or plan approval isn't repeated here: the header and its row already say it. With no records in 5 minutes and no working session, the card collapses into one line. The ⓘ can also be opened from the keyboard.
- **Speed now**: at the end of the line under the title, as in `Speed now · Install guide 55.6 generation tok/s`, named by the row's title (a subagent's by its project). It's the single most recent measurement received within 2 minutes among the visible working rows (subagents included), using only a value measured with that row's current model and leaving out clients waiting for a restart. Sessions are never summed or averaged, and it's never derived from log timestamps. Without such a measurement, `No measured speed` appears only when there's a row that's working, running a tool or retrying the API (with the reason in its help: no measurement in the last 2 minutes, measured with the previous model, or a restart needed), and it's hidden when rows are only waiting for input or logs, or nothing is working. When space runs short the label is dropped first, then the title. The help gives the session's title and project, model, measurement time and basis, and VoiceOver reads the unit kind, value and title.
- **Session list**: working sessions go on top, and the order doesn't change while the pointer is over the list or a menu is open. Output is an event, not a state, so it has no chip of its own: with a record just now (within 5 seconds), the row shows a green dot and `+617 tok · just now`, and after that the last record without a dot, as in `+617 tok · 10s ago`.
  - Working rows: the state glyph in the glyph column and the session's title (else its project) and a short ID on the text column shared by every row, the output so far this turn (the largest text); the second line opens with the state in words (`Waiting for plan approval`, `Waiting for an answer`, `API retry`, a tool category such as `Running command`, `Working`, `Waiting for log`), then the project (when the title is the session's own), the client, model and Codex effort, and ends with the turn's elapsed time (on rows needing input, how long they've waited, `m:ss`); then the last record and context (for Codex, `Context 61% used` against the recorded window, orange at 85% or more; Claude Code doesn't record its window size, so an absolute `Context 182k`).
  - The speed column appears only when at least one visible working row has a measurement (from a client not waiting for a restart). An unknown value is `— tok/s` (with the unit, so it doesn't read as a divider) and is never estimated from log timestamps, and this placeholder appears only on rows that may be generating: working, running a tool or retrying the API. Rows waiting for input or logs show a speed only when they have a measured value, and a third line is never added just for the speed column.
  - Idle rows: the session's title (else its project) with the project after it, the client, the output of the last completed turn (`Last turn 4.8k`) and its age (fixed width, so `Last turn` sits in the same spot on every row). `No end record` and `Interrupted` are told apart by ring glyphs, and also written in small text after the client when there's room.
  - Subagents follow their exact parent session with tree guides. Each is titled by a distinguishing role or nickname (the Codex role or nickname, the `agentType` from the Claude Code sidecar, `Auto review` for Codex automatic review); without one (or with a common role) it reads `Subagent · a2222222`, its 8-character ID beside it. On the right are the last record's age and the output this turn. Every running subagent is shown, and those waiting for logs are grouped as `+N subagents waiting for log ⌄`, which expands the list at that group.
  - The collapsed list ends with its one disclosure row: `Show all N sessions ⌄` when sessions are folded away, `Show N more subagents ⌄` when only subagents no `+N` line offers are, and `Show less ⌃` once expanded. The expanded list splits sessions that aren't working into `Today`, `Yesterday`, `This week` and `Earlier`, with `Earlier` collapsed. Rows have a fixed height, and the list shows up to 312 pt (the full remaining height in the panel) and scrolls the rest.
- **Row details and menu**: click a row or press Return to open inline details (copy the session ID, agent, model, running tool name, the last completed turn's output and duration, record times), with `Copy Resume Command` and `Show in Finder` (the project folder, else the log file) buttons when they apply. The two values are never divided into a speed. Right-click (VoiceOver actions included) offers `Copy Session ID`, `Copy Agent ID`, `Copy Resume Command` (`cd '<path>' && claude --resume <ID>` or `codex resume <ID>`, main sessions only, and not offered when the path or ID contains a backslash or control character, since a shell or terminal could read it differently), `Show Log File in Finder` and `Show Project Folder in Finder`. The other resume commands are `opencode --session`, `gemini --resume`, `copilot --resume`, `amp threads continue`, `grok --resume`, `hermes --resume`, `kimi -r` and `goose session --resume --session-id`; Qwen Code, Cline, omp, Droid, Cursor and OpenClaw have none, nor does a row shown under another product's name (TRAE CLI, OpenClaude, Qoder, Kilo Code, MiMo Code, Kimi Work, Kimi CLI and the like). File contents are never opened. On the keyboard, ↑↓ moves, Return or Space opens details, ⌘C copies the ID and ⌘⇧C the resume command (on macOS 13, click the list once first).
- **System**: at the bottom, without a box, CPU, memory, storage, battery and network (↓ value on top, ↑ below, one decimal under 10) are shown with meters of one length. CPU marks its 30-second peak with a tick when it's at least 5 points above the current value. The memory color follows macOS memory pressure (normal, warning, critical), not usage. Click the area to open Activity Monitor. IP addresses appear only in the help.
- **Bottom**: a single status item (AI collection delay > system collection delay > telemetry problem > `Restart Codex and Claude Code for speed`), shown only when there's one or an update notice; with everything live the row is hidden, and how often TokenCat checks and when telemetry last arrived are in the header sentence's help. Telemetry problems are buttons by cause (`Telemetry off · port in use`, `Telemetry off · another TokenCat`, `Telemetry off · collector error`, `Telemetry off · config conflict`, `Telemetry off · connection failed`, `No telemetry · check needed`), and clicking one opens the Telemetry tab in Settings. When a new version is out, a quiet extra line that doesn't compete with session state is added (`New version 1.0.0`, `Update`, and a close button that hides that version only); while in progress it shows `Downloading update 45%` or `Installing…`, and on failure `Update failed` with `Try Again` and a way to open the release page ([Updates and distribution](#updates-and-distribution)).
- **First launch, empty and loading**: the first time, a card that states only actual results is shown, one line per point with the explanation in each line's help (only metadata is used; the telemetry connection result, with `Show backup` once telemetry was added, and the reason and an emphasized `Open settings` when connecting was skipped or failed or the collector is down; whether the Claude Code status line was wrapped is in that line's help; it goes online only to check GitHub for new versions and to ask OpenAI and Anthropic for usage, which can be turned off in Settings), and ✕ closes it. While loading, placeholder rows, value-width placeholders and `Preparing` at the bottom are shown. With no records in the last 5 minutes, the output card collapses into one line, with `Last output …` on the right only when there was earlier output. A missing log folder is told apart from having no records, both with a client-neutral title (`No coding agent sessions yet`, `Couldn't find any coding agent log folders`): with no records, a note about starting a new session is shown; with no folder, one line naming the supported clients (the folders searched are in its help) and a `Check Again` button; both say that Claude web and desktop chats aren't collected.
- **Accessibility**: with Increase Contrast, faded text, borders and dotted rings are darkened, and states always use color and shape together. Informational text targets 4.5:1 and state glyphs and meters 3:1, measured on fixtures (the complete and no-recent-activity dots count as decoration and are darkened only with Increase Contrast). A VoiceOver rotor and row labels are provided, and Reduce Motion is respected.

### Menu bar

Choose a layout from **Minimal** (the character, AI state mark and session count, about 72 pt, or about 49 pt with the character hidden), **Two Lines** (the default, about 272 pt with the six default items) and **One Line** (about 410 pt with them). Minimal always shows AI, whatever the item list. Each item has a fixed width so its position doesn't shift when values change, and common maximums ('100%', three-digit network values with units) are drawn without shrinking.

It shows CPU, memory, storage, battery, upload/download and AI session count. The Average speed item (off by default, `Average speed · AVG` in the item list, whose tooltip says what it averages) is an explicit opt-in: the arithmetic mean of every session's own measured rate that `Speed now` would accept (fresh within 2 minutes, on the session's current model, client not waiting for a restart), across all clients; it only averages measured rates and never estimates one. Its label shows which clients contributed a rate, fastest first (by each client's own mean): one client's icon, or up to three whole icons side by side, 1 pt apart; the help names them (`Average speed 55.6 tokens per second · Codex, Claude Code`). Without a measurement it shows `AVG` (a speedometer symbol on one line) and `—`. From 100 tok/s up the bar drops the decimal (`312 tok/s`); the item adds 56 pt on two lines and 91 pt on one, so a four-digit speed beside three icons isn't shrunk. Two Lines fixes the column of network arrows and right-aligns the numbers, and units and '%' are drawn small but never omitted. Labels and units use the label color at 72% (80% with Increase Contrast), which follows the bar's light or dark appearance, so they don't turn flat gray on tinted bars as the secondary label color would. Network values use one decimal under 10. Network sums the physical Wi-Fi and Ethernet interfaces and excludes local loopback and VPN virtual interfaces. On a Mac without a battery, the battery item is hidden.

The AI number is the count of top-level sessions that are working or waiting for input (subagents count toward their parent), and `—` before the first collection. While any of them waits for input, it counts only those (the sessions you need to answer); the tooltip and VoiceOver value keep the full breakdown. With nothing working and only sessions waiting for logs, it shows the number waiting for logs in faded text; otherwise a faded `0`. The mark uses the same glyphs as the dashboard: a purple ring (working), a blue rounded square (running a tool), a gray half circle (waiting for log), a yellow `?` (input needed). Output is an event, so it has no mark. `No end record` isn't shown. The mark's slot is always reserved so the number never moves. While the dashboard is open, the mark loses its color and only its shape is drawn in the label color, and with Increase Contrast, the filled tool and input marks get a label-color border and the waiting-for-log half circle is darkened. The tooltip contains only capacities, an AI summary and how to use it; live values are provided as VoiceOver values.

At the top of the right-click (⌃-click, or the item's `Quick menu` action in VoiceOver) quick menu are `AI sessions · Input 1 · Tool 1 · Working 1` (or `No active sessions` when there are none) and up to three top-level sessions in order of urgency (`project — Waiting for input · 3m`, in minutes); choosing one selects that row in the dashboard. When more are live, `9 more sessions…` follows and opens the dashboard. Below are Open (⌥ Open as Panel) / Layout / Character (pick one · Show in Menu Bar) / Motion Source / (when a new version is out) `Install Update 1.0.0…` / Settings… (⌘,) / Activity Monitor / About TokenCat / Quit TokenCat (⌘Q). The update item is hidden while downloading or installing, and after a failure that a retry won't fix (running from a temporary location, no write permission, no release file or checksum, and so on), it becomes `Update 1.0.0 Release Page…` and opens the release page. When a newer version is found, that failure is cleared and installing is offered again.

### Character

Every character (cat, dog, hamster, penguin, robot) moves the same way; the cat stands for all of them below. The motion source is **AI Activity** (default), CPU Usage, Measured AI Speed or Still. AI Activity uses a fixed pace for each state and doesn't indicate speed. Working and running a tool are a walk (0.15 seconds per frame), newly recorded output is a 1.2-second run (new output during a run, or within 1 second after it, keeps it running), input needed is sitting and facing you, waiting for log is sitting (blinking at intervals cycling through 6, 9.5, 4.5, 11 and 7.5 seconds, twice every fourth time), and 10 minutes without activity is sleep. Sleep breathes for 20 minutes, alternating a small z and a big z, then holds the big z and stops the animation timer. The cat yawns once when it wakes, and blinks once, content, when it sits after a turn ends. Walking and running change only after holding for at least 1 second, while input needed changes immediately. With CPU, it sits under 4% and moves faster as usage rises; with measured speed, it sits when there's no measurement within 5 seconds. The old 'Measured AI Speed' default and the 'CPU Usage' that earlier versions stored as the default are moved to AI Activity once, and a value you pick yourself afterwards is kept. With Reduce Motion on, only the pose changes, and yawns, blinks and breathing are skipped. The timer stops when the cat is hidden, the display sleeps or the menu bar is covered, and yawns or content moments from that time aren't replayed later.

### Settings

Settings is a window with toolbar tabs that remembers the last tab and fits its height to the content. Values are stored in UserDefaults.

- **General**: Open TokenCat at login (off by default; registers as a macOS login item (SMAppService) only when you turn it on, then reads back and shows the actual registration state; installing in /Applications is recommended). Notifications: Turn complete / Input needed / Sound for input-needed alerts (all off by default, asking for permission only when you turn one on), and a permission row (with `Open Notification Settings` in that row when macOS blocks alerts or sounds). At the bottom, in its own section because it covers the Menu Bar and Character tabs too, `Restore Defaults…` (runs after confirmation, undo with ⌘Z; restores item order and visibility, layout, the character, and notification choices including `Notify about new versions`, and leaves the login item, `Check for updates automatically` and the macOS notification permission alone).
- **Menu Bar**: a 1:1 preview (light and dark), width, a preset (Minimal, AI Focus, System Monitor, All on One Line: sets the layout, the shown items and their order, and the character's visibility in one step; `Custom` when none matches), layout, and the item list: first the character (its own checkbox with the sprite, fixed in place since the bar always draws it first), then item visibility, order and abbreviations. Reorder by dragging or with VoiceOver actions. At least one of the character and the items stays shown, so the last one can't be hidden. Under Minimal, which draws only the character and AI, the item rows are dimmed and don't drag. On a Mac without a battery, the battery item is off.
- **Character**: the character (cat, dog, hamster, penguin or robot, all with the same poses and pace), motion source, and a legend of poses by state (plays on hover). Whether the character shows is in the Menu Bar tab's item list.
- **Telemetry**: collector status (`On · 127.0.0.1:16493` with an outline check when it's listening; the retry and its `Retry Now` on a row of their own under it), whether each client's measurements are arriving (`Nothing received yet` with a dashed circle) or need a restart, with a folder button that shows that client's config file in Finder, the `Claude limits` row (last received, recorded by the Claude desktop app, recorded by omp or Pi, nothing received yet, skipped because the statusLine format is different, the status line may look empty because the original command is unknown, the original command was recreated from the backup record), a note that only usage limits are received from the status line, `Show Backup Folder`, then `Connection` with `Disconnect…` (after confirmation, does what `--disconnect-telemetry` does, off the main thread, and stops automatic connection) or, once disconnected, `Reconnect`, and `Live usage limits` (on by default; checks usage with OpenAI and Anthropic using Codex and Claude Code's saved sign-in, every minute while in use and every 10 minutes otherwise, and never stores tokens; see [Live usage limits](#live-usage-limits)). The folder buttons never open the files. For a client whose settings changed, the notice clears when that client's first telemetry (including records that couldn't be parsed) arrives. If nothing arrives within 24 hours, it changes to 'No telemetry from this version' only if there's a record of that client actually being used after the settings change; clients that weren't used are left quiet.
- **About**: icon, version, the privacy statement as three left-aligned lines (what is read, where it goes online, what Live usage limits asks), MIT License, Show Welcome Again (the About TokenCat window is in the ⋯ menu and the quick menu). Updates: `Check for updates automatically` (on by default), a status line (`Up to date · Checked 3m ago` with `Check Now`, or `New version 1.0.0` with only a prominent `Update`; on an install failure, a warning mark and the full sentence, with `Try Again` and `Open Release Page` when a retry might help, otherwise `Open Release Page` (or `Open Applications Folder` when running from a temporary location) and `Check Now`), and `Notify about new versions` (off by default; when the macOS notification permission is off, it says so, with `Open Notification Settings` in the same row).

Notification titles are `Input needed · project` / `Turn complete · project` / `Turn interrupted · project`, the subtitle is `Claude Code · model`, and a completion body is `12,480 tok · 4m 12s`; the question or response text is never included. Each session keeps only the latest input-needed notification and the latest turn complete or interrupted notification, the input-needed notification disappears when you answer (on relaunch, such notifications left by the previous run are cleaned up too), and clicking one selects that row. Nothing is sent while the dashboard is actually visible. A new-version notification is sent once per version, without sound. While the dashboard is visible and VoiceOver is on, input needed and turn complete are announced at most once every 5 seconds.

### Language

Screens, menus, notifications, help, VoiceOver labels and command-line output are in English and Korean, with both texts side by side in the code (`loc` in `Localization.swift`). The language is picked once at launch and kept until quit. The app bundle has `en` and `ko` localizations and follows the language macOS picks, so TokenCat alone can be set in **System Settings › General › Language & Region › Applications**; otherwise it's whichever of Korean and English comes first in your preferred languages, and English if neither is listed. `--language en|ko` fixes the language for any command, including the checks and snapshots. Date and number formats use the display language with this Mac's region. The GitHub update request's `Accept-Language` is `en` regardless of the display language.

### Assets

The menu bar cat (runner v2, manifest v3) and app icon v2 are generated deterministically by the Swift code in `Assets/Generator`, with the palette defined in one place (`Palette.swift`). The runner is pixel art with white fur, a charcoal outline and a cobalt collar, with seven poses (sit 2, sleep 2, walk 4, run 6, sit facing you 2, yawn 1, content 2 frames), drawn 1:1 without blur in a 32 × 20 pt cell. The dog, hamster, penguin and robot each have their own sheet (`runner-<id>`, drawn in `Assets/Generator/Runner<Name>Art.swift`) with the same cell, poses and frame counts, and share the cat's manifest and effects; a character whose sheet is missing or fails its checks is drawn as the cat. The sleep z is an effects layer separated from the sprite (`runner-v2-fx`), drawn in the same 72% label color as the menu bar's labels and units (the full label color with Increase Contrast or while the item is open). Frame times and the blink rhythm are also read from the manifest. The dashboard header and the first-launch card use the same four pixel heads (normal, blink, alert, sleep), and the About tab in Settings shows the app icon. The app icon puts the existing cat mark (app-mark-v1, from a built-in image_gen original) on a macOS 26-style tile that runs from indigo to slate, and the 16 and 32 px sizes use the same pixel head as the menu bar cat. On macOS 13–15, the 16 and 32 px icons may look slightly larger than other apps' and appear as a square without a shadow. Vector master v3 only generates previews and isn't used in the build. Generation commands, palette, measurements and SHA-256 values (as of macOS 27.0.1 and Swift 6.4) are in [`Assets/runner-v2.md`](../Assets/runner-v2.md) and [`Assets/app-icon-v2.md`](../Assets/app-icon-v2.md). The README preview images are made by [`docs/Generator`](Generator/README.md) from synthetic snapshots, and images with text are kept per language in `docs/images/en/` and `docs/images/ko/`.

## Token metrics

Sessions, models, output tokens and progress are read from the local JSONL records in `~/.codex/sessions` (`$CODEX_HOME/sessions` first) and `~/.claude/projects` (first each folder `CLAUDE_CONFIG_DIR` names, comma-separated, then `~/.config/claude/projects` or `$XDG_CONFIG_HOME/claude/projects`). A Claude Code `<session>.orphaned-*.jsonl` copy is skipped. Token generation speed is never estimated from gaps between log timestamps. A whole turn's time includes tool runs and waiting, so it's never shown as a generation speed, and diagnostic output never contains speeds derived from log timestamps either. Turn time uses only values recorded by the client and is never divided into the output. Without real measurement data, the speed is `—`.

Products that write the Codex or Claude Code format are read the same way and named as themselves: **TRAE CLI** (`~/.trae/cli/sessions`, `TRAEX_SESSIONS_DIR`) in Codex's format, **OpenClaude** (`~/.openclaude/projects`, `OPENCLAUDE_CONFIG_DIR`) and **Qoder** (`~/.qoder/projects`, `~/.qoder-cn/projects` and the IDE's `~/Library/Application Support/Qoder/SharedClientCache/cli/projects`) in Claude Code's. Their rows carry no Codex or Claude usage limits, since a fork's limits aren't that subscription, and no resume command. Telemetry setup still edits only `~/.codex/config.toml` and `~/.claude/settings.json`.

Other coding agents are detected automatically by their data folders, with no setup: OpenCode, Kilo Code and MiMo Code (`~/.local/share/opencode`, `~/.local/share/kilo`, `~/.local/share/mimocode`), Gemini CLI (`~/.gemini/tmp`, and `~/.cache/.gemini/tmp` under its macOS sandbox), Qwen Code (`~/.qwen/projects`), Copilot CLI (`~/.copilot/session-state`), Amp (`~/.local/share/amp/threads`), Cline, Roo Code, Kilo Code, Zoo Code and IBM Bob (`globalStorage/<extension>/tasks` in every VS Code-style editor, `~/.cline/data/tasks`, `~/.cline/data/sessions`), omp and Pi (`~/.omp/agent/sessions`, each `~/.omp/profiles/<name>/agent/sessions`, `~/.pi/agent/sessions`), Factory Droid (`~/.factory/sessions`), Cursor (`~/.cursor/projects`), Grok (`~/.grok/sessions`), Hermes (`~/.hermes`), OpenClaw (`~/.openclaw/agents`, older `~/.clawdbot` and `~/.moltbot`), Goose (`~/.local/share/goose/sessions`) and Kimi Code (`~/.kimi-code/sessions`, the Kimi desktop app's `~/Library/Application Support/kimi-desktop/daimon-share/daimon/runtime/kimi-code/home/sessions`, the archived kimi-cli's `~/.kimi/sessions`). The clients' own variables move those folders: `XDG_DATA_HOME`, `OPENCODE_DB`, `KILO_DB`, `MIMOCODE_HOME`, `MIMOCODE_DB`, `GEMINI_CLI_HOME`, `QWEN_RUNTIME_DIR`, `QWEN_HOME`, `COPILOT_HOME`, `AMP_DATA_DIR`, `CLINE_DIR`, `CLINE_DATA_DIR`, `CLINE_SESSION_DATA_DIR`, `PI_CODING_AGENT_DIR`, `PI_CONFIG_DIR` (with `$XDG_DATA_HOME/omp` when set), `PI_CODING_AGENT_SESSION_DIR` (Pi), `FACTORY_HOME_OVERRIDE`, `CURSOR_CONFIG_DIR`, `GROK_HOME`, `HERMES_HOME`, `OPENCLAW_STATE_DIR`, `OPENCLAW_HOME`, `OPENCLAW_PROFILE`, `GOOSE_PATH_ROOT`, `KIMI_CODE_HOME` and `KIMI_SHARE_DIR`; the default folder stays listed beside each override. Each one's log reader is registered in the provider registry (`TokenProvider.all` in `TokenProviders.swift`, `TokenProvider.All` on Windows), and every agent listed is read as below. A detected agent is named in the AI item's per-client counts. Telemetry connects Codex, Claude Code, Gemini CLI and Qwen Code; live usage limits and the status line bridge stay Codex and Claude Code only; the average speed item and AI session counts include every agent that is read.

- **Gemini CLI**: the `session-*.jsonl` chats in `~/.gemini/tmp/<project>/chats` (under the macOS sandbox, `SANDBOX=sandbox-exec`, `~/.cache/.gemini/tmp`; older `session-*.json` snapshots until they're resumed) and the subagent logs in their `chats/<session>/` folders; the project comes from the folder's `.project_root`. A turn runs from your prompt to a reply without a tool call; a reply that only asks for tools shows as running a tool, because Gemini CLI writes tool calls when they finish. Output is candidate plus thinking tokens. Questions and permission prompts aren't logged while they wait, and neither are generation times, so Gemini CLI never shows `Input needed`, and its speed comes only from its own telemetry once connected (below). An open turn with no new record shows `Waiting for log` after 10 minutes (15 while a tool runs).

Tool calls and results are logged as they happen, so running tools show, and a pending question (`ask_user_question`) or plan approval (`exit_plan_mode`) shows as `Input needed`. Context is a share of the recorded window; reasoning already inside the candidate count isn't added twice. No generation times are logged; its speed comes only from its own telemetry once connected (below).

A turn runs from your message until `session.task_complete`, or a turn end whose last reply asked for no tool; `abort`, an error or shutdown interrupts it. Running tools show, and a pending permission prompt or `ask_user` shows as `Input needed`. The log gives the project, turns and running tools (a reply with text and no tool call completes the turn); the settings file gives the model, effort and the session's output total. Kilo Code and MiMo Code rows carry their own names. A prompt larger than 64 KB (one carrying file diffs) is never loaded. In the OpenCode 2 format the end is the recorded stream end, else the step's completion when it ran no tool, else the last tool's start; without one of those no speed is shown. Permission prompts aren't recorded, so they can't be shown.

A CLI session's turn state comes from its manifest `status`. None records generation times, so no speed is shown.

A turn runs from your prompt to a reply that stops without tool calls; running tools show with their category, the `ask` tool shows as `Input needed`, and an aborted or failed reply interrupts it. A subagent ends with its exit record. Output, context (input plus cache) and the thinking level come from each reply. omp records each request's duration and time to first token, so a reply gets a measured **request tok/s** (output ÷ request time, first-response wait included) without the collector. A log whose first read starts mid-turn shows that turn's output as unknown.

Transcripts carry no times, so a record takes the file's write time (a prompt's leading timestamp tag gives the turn start to the minute). Output tokens and context come per model call from the unified log's `inference_done` lines, and each call's **request tok/s** is its output over Grok's own measured call time (first-token wait included). When the unified log no longer covers a turn, only the turn's total from `turn_completed` is shown, without a speed. Subagent sessions are grouped under their parent.

A conversation Hermes split by compression stays one row. A prompt opens a turn, a reply's tool calls show the running tool (Hermes writes a call only together with its first result, so a lone running tool shows as working), `clarify` shows as `Input needed`, and the reply's finish reason completes or interrupts the turn. Output is the growth of Hermes's session output total (reasoning included) between reads, so output that came before TokenCat's first read stays a baseline. Context and a **request tok/s** (output ÷ Hermes's recorded latency, flagged as including retries when one came first) come from the newest `API call` line for the session in `logs/agent.log`, so they appear only while that log holds its recent calls. The model follows `/model` switches; the title is shown only when the model or you set it (a `derived` title is the first prompt and is never shown). Subagents are grouped under their parent. Approval prompts live only in memory, so they can't be shown.

A prompt opens a turn, a reply with tool calls shows the running tool, `ask_user` shows as `Input needed`, and the reply's stop reason completes or interrupts it; OpenClaw's own bookkeeping replies are skipped. Output is each reply's recorded output, but recent versions store large entries zstd-compressed, which TokenCat can't decode, so a turn with such a reply gets its output only when the run ends, from the session's own total. Spawned subagents are grouped under the spawning session. OpenClaw records no request durations, so no speed is shown, and exec approvals aren't recorded.

A prompt opens a turn, running tools show by name, approval and question requests show as `Input needed` until resolved, and the turn end completes or interrupts it. Output and context come from each turn-scope usage record; the model is the id sent to the provider. Subagents (`agent-N`) are grouped under their session. Sessions Kimi Code already migrated from kimi-cli are shown once, from Kimi Code's copy.

At startup, TokenCat confirms the local collector is ready, then automatically adds the OpenTelemetry exporter to Codex `~/.codex/config.toml` and the telemetry environment variables to Claude Code `~/.claude/settings.json`, and wraps the Claude Code `statusLine` command with the [status line bridge](#claude-usage-limits-and-the-status-line-bridge). When `~/.gemini` or `~/.qwen` exists, it also sets the `telemetry` object in Gemini CLI `~/.gemini/settings.json` or Qwen Code `~/.qwen/settings.json` (created if missing): `enabled: true`, `target: "local"`, `otlpEndpoint: "http://127.0.0.1:16493"`, `otlpProtocol: "http"` and `logPrompts: false` (both clients log prompt text unless it's off), keeping every other key. A Gemini CLI or Qwen Code file that isn't plain JSON (both clients allow comments, which TokenCat can't keep), repeats a key, has a non-object `telemetry`, or already exports somewhere (its own `otlpEndpoint`, `otlpLogsEndpoint`/`otlpTracesEndpoint`/`otlpMetricsEndpoint`, an `outfile`, `target: "gcp"`, or `enabled: true` with no endpoint, which sends to their default `localhost:4317`) is left as it is: that client is skipped with the reason in Settings › Telemetry, and the other clients still connect. `GEMINI_TELEMETRY_*` and `QWEN_TELEMETRY_*` environment variables override these settings and TokenCat can't see them. Every client applies it **from its next launch**, and work in progress isn't restarted. TokenCat has to be running to receive data. If the collector isn't ready, client settings aren't changed. A client installed after the connection joins it on TokenCat's next launch, under the same backups.

The collector accepts POST (`Content-Type: application/json`) on `127.0.0.1:16493` for OTLP HTTP/JSON `/v1/logs`, `/v1/metrics` and `/v1/traces` and the status line bridge's `/v1/claude/status`, and answers TokenCat's own check endpoints `/health`, `/v1/readings` and `/v1/diagnostics` only to GET. Bodies come with `Content-Length` or `Transfer-Encoding: chunked` (Gemini CLI and Qwen Code's Node exporters send no length); a request with both, another transfer coding, broken chunk framing or bytes after the last chunk is refused. It isn't opened on external interfaces, and it rejects requests that carry a web page Origin or a `Host` other than `127.0.0.1` or `localhost` (so a DNS-rebinding page can't read it). Prompt and response text logging is turned off, and only allowed metadata such as models, session, agent and request identifiers, times and output tokens are kept in memory. Raw requests are never written to files, and from `/v1/claude/status` only the usage limit numbers are kept and the rest discarded (those numbers are the only thing that reaches disk). Measurements are kept as the latest 256 plus, for each (provider, session, agent, model), the newest one, up to 128 entries; when that overflows, subagent entries are evicted first, so a flood of subagent requests never wipes out a main session's last speed. `/v1/diagnostics` keeps up to 64 entries of received counts and service and metric names, units and whether they were recognized, and for unrecognized services keeps only span and event names and attribute keys, never values. Limits are a 2 MB HTTP body (64 KB for `/v1/claude/status`, 413 beyond that; chunk framing may add at most as much again), 16 concurrent connections and a 5-second request limit, and connections are released on quit. If the port isn't available, it retries after 5 and 30 seconds, then every 2 minutes until the port frees up, and shows whether another TokenCat is collecting or another app is using the port.

Displayed units are separated by the basis of the measurement.

- **generation tok/s**: the inverse of the actual time between tokens (TBT) provided by the Codex server. Uses `codex.responses_api_engine_service_tbt.duration_ms` or `codex.responses_api_engine_iapi_tbt.duration_ms`.
- **model tok/s**: when a server metric bundles several observations, computed from the average time between tokens. The observation count and measurement window are shown in the help. Statistics over several requests are never attributed to a single session's speed.
- **request tok/s**: the processing rate from the output token count Claude Code provides in the same `api_request` event, divided by the actual successful request time; for Gemini CLI (`gemini_cli.api_response`) and Qwen Code (`qwen-code.api_response`), the response's `output_token_count` (plus `thoughts_token_count` when `total_token_count` shows thinking was counted apart) divided by its `duration_ms`, which runs from the request to the end of its stream; or, for OpenCode, omp, Grok, Hermes, Goose and Kimi Code, a reply's output tokens divided by the request time they record in their logs. It includes the wait for the first response and reasoning. When only a trace is provided, it's marked as a request time that includes retries. Its basis differs from a pure generation speed.

When first-token latency and server inference time are provided, the raw values can be seen in the help. A generation speed is never built from first-token latency alone. Codex SSE event processing time is never used as model generation time. The latest completed measurement is shown, so it doesn't mean the instantaneous speed of output in progress. The Codex desktop app (codex-app-server) sends logs and traces, but TokenCat couldn't confirm a per-request generation time format, so its speed shows as `—`.

A measurement is attached to a log row only when the provider, session and agent identifiers match exactly. Rows are never linked by model name or closeness in time. Claude Code always attaches an agent identifier to subagent requests, so a request without one is linked to the only main log of the same session. Gemini CLI and Qwen Code send their subagents' requests under the parent's session ID, so only main-conversation requests are read (Gemini CLI's `role: "main"`, or no role in older versions; Qwen Code's requests without `subagent_name`) and they attach to that session's only main log; Gemini CLI's routing, loop-detection and other utility requests are skipped too. When one row has measurements from several models, the row's current model takes precedence, so side requests such as title generation don't hide the current model's speed. A server metric without a session identifier is shown as a **Model measurement** row, and identifiers not linked to a log stay as a **Request measurement** row. When a session's model changes, the current model is told apart from the previously measured one. TokenCat follows the official [Codex OpenTelemetry configuration](https://learn.chatgpt.com/docs/config-file/config-advanced), the [Claude Code monitoring spec](https://code.claude.com/docs/en/monitoring-usage), [Gemini CLI telemetry](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/telemetry.md) and [Qwen Code telemetry](https://github.com/QwenLM/qwen-code/blob/main/docs/developers/development/telemetry.md). Depending on the client version or server response, metrics or identifiers may not be provided.

Before connecting, the original settings are backed up to `~/Library/Application Support/TokenCat/telemetry-backups/` with restricted access (folder 0700, files 0600). Other settings such as authentication, models and hooks, and file permissions, are kept. An existing external telemetry destination that would conflict is never overwritten. The diagnostic command `--disconnect-telemetry` restores the original bytes of config files that haven't changed since connecting, and removes the bridge script and the original command file. For files modified after connecting, it keeps the current bytes in the backup folder as `before-disconnect-<time>-<backup name>` (0600) and then reverts only the TokenCat entries. For Codex, it removes the `[otel]` table TokenCat appended at the end, together with the blank line before it, when they are byte-for-byte unchanged and have no other keys; for Claude Code, it restores keys in `env` that still hold TokenCat's values to their backed-up values (removing them if there were none), and restores text logging keys that TokenCat set to `0` to their backed-up values; for Gemini CLI and Qwen Code, it restores the `telemetry` members that still hold TokenCat's values (`enabled`, `target`, `otlpEndpoint`, `otlpProtocol`, `logPrompts`) to their backed-up values, removing them, and `telemetry` once empty, if there were none. A Gemini CLI or Qwen Code file edited after the connection so that TokenCat's members changed is not written again on the next launch; Settings › Telemetry says it was skipped. If a TokenCat key was changed to a value that's neither TokenCat's nor the original, the original Codex settings already had an `[otel]` table (TokenCat's keys mixed into it) or the appended lines changed, or a modified Claude Code settings file still points to the bridge after the status line step below (the connection record is kept), no file is changed and the file names are reported. In every case, if Claude Code's `statusLine.command` is still exactly the bridge command TokenCat wrote, that entry is reverted first. If the file is unchanged since the bridge was added, the bytes from before the change are restored; otherwise the recorded original `statusLine` object is put back (the key is removed if there was none originally), leaving other keys as they are now. When possible, only the command string is replaced so the formatting is kept, and the file from just before the change is kept in the backup folder as `claude-settings-before-statusline-restore-<time>.json` (0600). After that, if nothing points to the bridge, the bridge script and the original command file are removed, and the outcome is appended to the end of the result or error sentence (`Restored the Claude Code status line to its original command.`, `Removed the Claude Code status line TokenCat added.`, `The status line was also left as it is.`, or the location of the original command file if it couldn't be reverted). A status line that differs from the bridge command is left alone, and the script is kept as long as something points to the bridge, even written differently. Clean up the remaining telemetry settings of a refused file by hand using the backup, and don't delete `~/Library/Application Support/TokenCat/` while `settings.json` still points to `claude-statusline.sh` (the original command is inside it, and deleting it makes the status line fail to run). The restore takes effect from the clients' next launch. `--disconnect-telemetry` sets the `telemetryDisconnected` setting even when it's refused, so the app doesn't reconnect automatically, and `--connect-telemetry` clears it. `--connect-telemetry` connects right away only while a TokenCat collector is running; otherwise it ends without connecting, but the setting is cleared, so the app connects automatically on its next launch.

`Disconnect…` in Settings › Telemetry (after a confirmation) does the same as `--disconnect-telemetry` from inside the running app, off the main thread: it sets `telemetryDisconnected` first, restores the client settings, clears the restart notices and shows a refused restore in the tab's warning line. `Reconnect` in the same row clears the setting and connects right away, like `--connect-telemetry` with the collector running.

### Claude usage limits and the status line bridge

Claude Code doesn't send account usage limits through its logs or OTLP; it puts them only in the `rate_limits` of the JSON it passes to the status line command on standard input. `five_hour` and `seven_day` are present for Claude.ai subscription accounts after the first response. So when connecting, TokenCat wraps the `statusLine` in `~/.claude/settings.json` as follows.

- For `{"type": "command", "command": …}`, only `command` is replaced with `/bin/sh "$HOME/Library/Application Support/TokenCat/claude-statusline.sh"`, and other fields such as `padding` are kept. When possible, only the command string is replaced so the file's formatting is kept too. The original command is kept in `claude-statusline-command` (0600) in the same folder, and the replaced `statusLine` object in `statusLine.original` of the connection record `telemetry-connection.json`.
- With no `statusLine`, only the bridge is added. This bridge just forwards and prints nothing.
- If the command is empty or in another format, only the limit connection is skipped. A command that already points to the bridge isn't wrapped again even if its path is written differently, and a status line that someone changed or removed after it was wrapped once is left alone.
- An installation connected with a version before the bridge (0.8.0 or earlier) keeps the file from before the change (`claude-settings-before-statusline.json`) in the same backup folder on the next launch and only adds the bridge. If the original command file has gone missing, it's recreated from the connection record; if the settings point only to the bridge without a record (such as settings copied from another Mac), the status line will look empty and has to be fixed by hand. Skip reasons and notes like these appear in the `Claude limits` row in Settings › Telemetry and in the `--connect-telemetry` output.

The bridge script (0700) sends the JSON it receives, unchanged, with `curl` to `http://127.0.0.1:16493/v1/claude/status`. It doesn't use `~/.curlrc` or a proxy and sends in the background with a 1-second connect and 2-second total limit, so the status line never waits even if TokenCat is missing or slow. Then it runs the original command with the same input and returns its output and exit code unchanged. The JSON it sends also contains Claude Code status information such as the working folder, session ID, log file path, model and cost, but as soon as TokenCat receives it, it keeps only the two windows' `used_percentage` (0–100) and `resets_at` together with the time received, and discards the rest. These values are stored in UserDefaults `claudeUsageLimits` so they show on the next launch (removed with `defaults delete dev.seuput.TokenCat`), and for each window the value received later wins. They update only when Claude Code redraws its status line, so without a [live check](#live-usage-limits), the last value and its age are shown while you're not using Claude Code. After connecting, Claude Code has to reread its settings (usually after a new launch) before it uses the bridge.

Claude Code in the Claude desktop app doesn't run the status line. So TokenCat also reads, without writing, `~/Library/Application Support/Claude/plan-usage-history.json`, which the desktop app writes about every 15 minutes. It uses the time and the two percentages only when `version` is 2 and the last entry of `samples` has the form `{"t": <ms>, "u": {"fh": <5-hour %>, "sd": <7-day %>}}` (discarding `org` and earlier samples), and quietly ignores any other format or a file over 2 MB. It rereads the file only when its size or modification time changes. This history has no reset time, so none is made up; only `Recorded 5m ago` is shown, and a window counts as reset once its length (5 hours or 7 days) has passed since the record. For each window it's compared with the bridge value and the one with the later record or receive time wins, and bridge values use the actual reset time as is.

### omp and Pi usage history

omp and Pi check the limits of their own Claude and ChatGPT sign-ins and append each result to the `usage_history` table of `agent.db` in their agent folder (`$PI_CODING_AGENT_DIR`, `~/.omp/agent`, `~/.pi/agent`; `%USERPROFILE%\.omp\agent` and `%USERPROFILE%\.pi\agent` on Windows). TokenCat opens that database read-only and, per account and window, reads only the newest row's used fraction, reset time and record time: `anthropic:5h` and `anthropic:7d` become Claude's 5-hour and weekly windows, and `openai-codex:primary`/`secondary` become Codex windows, with the length taken from the window label (`7 days`, `5 hours`). Model-scoped weeks (`anthropic:7d:<model>`), extra Codex meters and other providers are skipped, and e-mail addresses, account IDs and labels are never kept. The database is queried again only when it or its WAL file changes.

- **One account**: per provider, the account checked last. omp's Anthropic rows are left out when their account ID differs from the one Claude Code is signed in to (`oauthAccount.accountUuid` in `~/.claude.json`, read only when that file changes), since those limits belong to another subscription.
- **Merge**: these are records, never live values. Each window is weighed with the other sources by recency, as above: a newer omp record replaces an older status line or desktop value, and for Codex an omp record newer than the last live read joins the log records of the same reset window.
- **Display**: the age is omp's or Pi's own record time, and the row names it (`… · omp recorded 4m ago`); the help says the value comes from that client's own usage check. The `Claude limits` row in Settings › Telemetry reads `omp · recorded 4m ago`.

### Live usage limits

`Live usage limits` in Settings › Telemetry (on by default, macOS and Windows) asks for each account's current limits instead of waiting for a log or status line record. A live value is used together with the sources above and wins over an older record of the same window. Turning it off stops these requests.

- **Codex**: for each check, TokenCat starts the local `codex app-server` (the Codex CLI), asks it for the account's rate limits (JSON-RPC `account/rateLimits/read`) and stops it. The Codex CLI talks to OpenAI with its own saved sign-in; TokenCat never reads Codex's tokens.
- **Claude**: TokenCat reads Claude Code's saved sign-in token, on macOS from the Keychain item `Claude Code-credentials` (through `/usr/bin/security`; macOS may ask for permission once, and if you deny it, TokenCat reads only `~/.claude/.credentials.json` for the rest of that run), otherwise from `~/.claude/.credentials.json` (`%USERPROFILE%\.claude\.credentials.json` on Windows), and sends one `GET https://api.anthropic.com/api/oauth/usage`. If that token is missing or expired, it uses omp's or Pi's saved Anthropic sign-in instead: the enabled `anthropic` OAuth entry in the `auth_credentials` table of `agent.db` in the same agent folders as their [usage history](#omp-and-pi-usage-history), reading only the access token, its expiry and account ID. That token is used only when its account ID matches the one Claude Code is signed in to (`oauthAccount.accountUuid` in `~/.claude.json`) or Claude Code's account is unknown, so omp and Pi keep the limits live while you work through them. The token is kept only in memory: it's never written, logged, put in process arguments or refreshed. A token that has expired or expires within 60 seconds isn't sent (Claude Code, omp and Pi refresh their tokens only while they run), after a 401 or 403 the same token isn't sent again until the saved one changes, and redirects are refused. Without a usable token, the [status line bridge](#claude-usage-limits-and-the-status-line-bridge), the desktop app's usage history and [omp's and Pi's usage history](#omp-and-pi-usage-history) still apply.
- **When**: every minute for a provider while a session on its models is running or the dashboard is open, otherwise every 10 minutes. A running session counts for the provider whose models it uses, whichever client runs it: Claude models for Claude, OpenAI GPT, o-series and Codex models for Codex (so an omp session on `claude-opus-…` keeps Claude's check at 1 minute). Opening the dashboard checks right away if the last check is 15 seconds old or more. Checks pause while the Mac or PC sleeps or the display is off, failures back off (up to 15 minutes on macOS, 30 on Windows), and each provider has at most one request at a time.
- **Display**: a live value up to 2 minutes old reads `… · live`; older ones keep `… · recorded 5m ago`. When the answer has no reset time, none is shown.
- **Nothing else is sent**: no usage history, device information or identifiers.

On macOS, `TokenCat --live-limits` checks each provider once and prints only the numbers, never the token, then omp's and Pi's newest records with their age and the limit rows both would give the dashboard.

### Sessions and states

Codex and Claude Code subagents are also collected separately and grouped under their exact parent session identifier (the shared session ID for Claude Code, the root thread ID for Codex). Even when a forked Codex log rewrites its parent's session metadata, it keeps its own identity from the thread ID in its file name, and the parent's rewritten usage limit and compaction records are excluded.

A session shows as working while it's within an allowance after the last log record of its open turn. The allowance is 10 minutes waiting for a model response, 15 minutes for a Claude Code tool run and 120 seconds for a Codex tool run, and every kind of log record counts. After the allowance it changes to `Waiting for log`, and 30 minutes after the last record to `No end record`. When Claude Code is waiting on a question (AskUserQuestion) or a plan approval (ExitPlanMode), it's `Input needed`, doesn't change to `Waiting for log`, and becomes `No end record` after 24 hours without a record. A question in Codex Plan mode (`request_user_input`) is also `Input needed` under the same rule, while the asynchronous `request_user_input_async` is treated as a regular tool. Permission prompts aren't logged, so they aren't shown. This doesn't say whether the OS process is alive, and file modification times are used only to detect changes, never as activity times.

Running tools are categorized by name alone into running a command, file operations, web lookups, subagents, MCP, questions and other. Tool inputs aren't read, and the original tool name appears only in the help. From Claude Code API retry records, only the retry count, maximum count, wait time and whether the network is down are read (`Retry 2/10 · in 4s`); error messages aren't stored, and the state clears when the next response arrives or the turn ends.

A session row is named by the client's own session title when there is one, with the project folder kept beside it (on a live row at the start of the second line; on a quiet row after the title, which is cut first); help, VoiceOver and `Speed now` name both. Only titles the client generated or you set by renaming are read, newest first, and they update as the client renames or regenerates them: Claude Code's `custom-title` (`/rename`) over its `ai-title` over an older `summary` record; Codex's thread names in `~/.codex/session_index.jsonl`; OpenCode's, Kilo Code's and MiMo Code's `session.title` once it replaces the `New session - <time>` placeholder (MiMo's fallback titles are dropped); omp's title slot and `title_change` records, Pi's `session_info` name; Gemini CLI's generated `summary`; Qwen Code's `custom_title` records; Copilot CLI's `workspace.yaml` `name`, else its generated `summary`; Amp's thread `title`; Droid's `session_start` title once it's generated or renamed; Cursor's generated chat name; Grok's generated or `/rename` title; Hermes's title set by its model or by you; OpenClaw's label or generated display name; Goose's generated, recipe or renamed name; Kimi Code's generated or custom title. Cline, Roo Code, Kilo Code's extension, Zoo Code and IBM Bob have none (their task title is the first prompt), nor do Kimi CLI sessions, a Droid session whose title is still its first message, a Hermes `derived` title, a Grok title that copies the first prompt, or a Goose session on a CLI or ACP agent provider until you rename it. A title is cut to one line of 80 characters, with control characters and invisible formatting removed; it's kept in memory only, never written to disk or sent, and `--diagnose` prints it with the other session metadata.

Codex usage limits use the usage percentage, window and reset time recorded in the logs, together with the record time. Claude usage limits use the values received through the [status line bridge](#claude-usage-limits-and-the-status-line-bridge), not the logs, together with the time received, and the Claude desktop app's usage history together with its record time. For both, a [live check](#live-usage-limits) is used with the time it was received, and [omp's and Pi's usage history](#omp-and-pi-usage-history) with its record time. For context, Codex uses the input tokens of the last response and the model context window from the same record, and Claude Code uses the sum of input and cache tokens. The Claude Code window size is never guessed from the model name, and for compaction only the time of the completion record is shown.

Token increases are reflected only when the log records them, and duplicate usage is never added again. Codex uses the `token_usage_record` written right after each response (per-response and turn-cumulative output), so it doesn't wait for tool runs to finish. Duplicates are removed by `response_id`, and `token_count` is used only in logs from earlier versions that lack this record. Claude Code records at the end of a message, so tokens being generated are reflected after the message completes. When a Claude Code log is long, TokenCat searches backward within up to 16 MB for the open turn's input and reads from there. The turn total shows `—` only when the whole current turn can't be checked. A turn's end is confirmed by Claude Code's end record, a subagent's turn-ending tool result, a final response without tool calls, or an API error or interruption record. If records continue after a final response (a Stop hook, for example), the same turn continues. Once completion or interruption is confirmed, the current turn's elapsed time and total are cleared. Earlier records rewritten by a session restore aren't reflected again.

### Collection scope and refresh

Claude Code's terminal and desktop launch paths are collected. Claude on the web and regular desktop chats take a different path from Claude Code, so they aren't collected. TokenCat reads the most recent log files, up to 32 for Codex and 32 main plus 32 subagent files for Claude Code (64 subagent files when they changed within the hour), and collects only what is appended afterwards. Sessions that are working or have records within the last hour keep being tracked even when there are many newer files (up to 256 tracked files in all). File change events (FSEvents) in the log directories trigger an immediate reread (at most 4 times per second), alongside a check every second and a new-file check every 60 seconds; a write to a log not yet tracked opens it at once. For a single line over 1 MB, the content isn't read; only the tool call identifiers at its start are checked. For long Codex logs, model and turn metadata are checked backward within up to 16 MB. Missing token spans are never reconstructed. System and log collection and local measurements each run on their own background queue, and memory pressure is read from the kernel's pressure level (normal, warning, critical).

TokenCat itself never calls a model or signs in to an account (the live usage check uses the sign-in Codex and Claude Code, or omp and Pi, saved), and it registers a login item or sends notifications only when you turn them on in Settings. Its internet access is the latest-version check for [updates](#updates-and-distribution), the downloads you click and, while `Live usage limits` is on, the [usage limit checks](#live-usage-limits) (OpenAI through the Codex CLI, and `api.anthropic.com`); all other communication, including the collector, stays on loopback (`127.0.0.1`).

In a real environment, receiving server TBT from Codex 0.160.0 and showing it on the native screen were confirmed. For Claude Code too, the output tokens, successful request time and first-token time of authenticated real requests were received and compared against local logs with the same session and request identifiers. For example, 200 output tokens / 4,532 ms for `claude-opus-5-5` is a request processing rate of 44.1 tok/s, which doesn't mean a pure generation speed. Without measurement data, no number is shown.

## Updates and distribution

Distribution is through GitHub Releases. `TokenCat.zip` is uploaded to the latest release tagged `v<CFBundleShortVersionString>` (for example `v0.9.0`), with `TokenCat.app` at the top of the zip; from 0.11.0 the same release also carries `TokenCat-Windows.zip` ([Windows](#windows)). The app is an arm64 and x86_64 universal binary (macOS 13 minimum) with only an ad-hoc signature, without Developer ID signing or notarization.

**Checking**: only one request is made, `GET https://api.github.com/repos/SeuPut0705/TokenCat/releases/latest` (`Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`, `User-Agent: TokenCat/<version>`, and `Accept-Language: en` fixed instead of the user's language list; macOS adds `Host`, `Accept-Encoding: gzip, deflate` and `Connection`). Downloading the release file sends only the same `User-Agent` and `Accept-Language`. From the response, only `tag_name`, `html_url`, `draft`, `prerelease` and the `TokenCat.zip` asset's `browser_download_url`, `size` and `digest` (`sha256:<hex>`) are read, and no identifiers or usage information are sent. When `Check for updates automatically` (on by default) is on, it checks about 5 seconds after launch, every 15 minutes (with timer tolerance), about 15 seconds after waking from sleep, and when you open the dashboard more than 5 minutes after the last check, with only one request at a time. When it's off, it asks only when you click `Check Now`.

**Rate limits**: the unauthenticated GitHub API allows 60 requests per hour per IP, and 304 responses count too. So TokenCat stores the last response's ETag and release information and asks with `If-None-Match`, and when a 403 or 429 comes with `X-RateLimit-Remaining: 0`, `X-RateLimit-Reset` or `Retry-After`, it pauses until that time. The reset time is measured against the response's `Date`, so a wrong Mac clock doesn't stretch it, and the pause is clamped between 1 minute and 1 hour. Network errors are retried at growing intervals of 1, 2, 4 and 8 minutes, up to 15 minutes, and checks after waking from sleep keep to these intervals too. `Check Now` skips the error interval but keeps to a rate limit pause. Clicking `Update` during a pause downloads with the release information already received, still checking the size and SHA-256.

**Installing**: happens only when you click `Update` (at the bottom of the dashboard, or in Settings › About) or `Install Update 1.0.0…` in the quick menu. TokenCat downloads `TokenCat.zip`, compares it with the SHA-256 in `digest`, and only if it matches replaces the app and relaunches. When it reopens, it shows `Updated to 1.0.0` once. Closing the notice line in the dashboard hides that version only, and with `Notify about new versions` on, a silent system notification is sent once for each new version (a newer version replaces the previous notification, and it's removed when an install starts or an update completes). If you quit during the `Installing…` step, TokenCat finishes that step (a few seconds, at most 60) before quitting, and a case where only the old copy of the app couldn't be deleted counts as installed. Settings (UserDefaults) and measurement backups live outside the app, so they remain after the replacement.

**Checking on push**: pushes to main and pull requests that touch `Sources/`, `Assets/`, `build.sh` or `Package.swift` run [`.github/workflows/macos.yml`](../.github/workflows/macos.yml) on `macos-26`: `./build.sh`, `--self-test` and `--telemetry-lifecycle-checks`.

**Making a release**: bump the version in `build.sh` and push to main, and [`.github/workflows/release.yml`](../.github/workflows/release.yml) runs. It reads the version and build number from `build.sh`, and does nothing if the `v<version>` tag already exists. Otherwise, on a macOS 26 runner (`macos-26`, the image's default Xcode), it prints the tool versions and goes through `./build.sh`, `--self-test` (also as x86_64 if the runner has Rosetta), `--telemetry-lifecycle-checks`, an arm64 and x86_64 check with `lipo -archs`, comparing the Info.plist version with the tag, and `codesign --verify --deep --strict`, then packs it with `ditto -c -k --sequesterRsrc --keepParent dist/TokenCat.app TokenCat.zip` and prints the SHA-256. The version check step stops if the new version isn't higher than the current latest release or has no `## <version>` entry in [`CHANGELOG.md`](../CHANGELOG.md). It builds release notes in English and then Korean (a one-line introduction, the version's `CHANGELOG.md` entry, a link comparing with the previous tag, terminal install instructions that check the SHA-256 first and Gatekeeper instructions, the automatic settings connection and status line wrapping on first launch with the disconnect command, and the SHA-256), creates an untagged draft with `gh release create --draft` (first deleting any draft with the same tag left by an earlier run), and publishes it as the latest release only if the draft asset's `digest` equals the zip's SHA-256. After publishing, it rereads `/releases/latest` a few times to confirm it returns the new tag with the same `digest`. Runs are grouped under a single concurrency group, `release`, so a release in progress is never cancelled. GitHub keeps only the newest pending run, though, so if you bump the version and push more than once during a release, the intermediate versions are skipped and only the newest is published.

**Gatekeeper**: because the app isn't notarized, `spctl -a -vv -t exec` assesses it as `rejected` whether or not it's quarantined, and `syspolicy_check distribution` reports `Adhoc Signed App` (warning) and `Notary Ticket Missing` (fatal) (confirmed on macOS 27.0.1). macOS applies this assessment the first time an app with the quarantine attribute (`com.apple.quarantine`) is opened, so a copy downloaded with a browser has to be allowed once, while a copy downloaded with `curl` and unpacked with `ditto -x -k` has no quarantine attribute and opens directly.

## Windows

The Windows version lives in [`windows/`](../windows) (C# on .NET 10, WPF plus the WinForms `NotifyIcon`, no third-party packages). It ports the Mac app's rules, not its UI; the design, the cuts from the Mac app and the PC checklist are in [`windows/DESIGN.md`](../windows/DESIGN.md). Installing and what differs for users are in [README › Windows](../README.md#windows).

- **Projects** (`windows/TokenCat.Windows.slnx`): `TokenCat.Core` (`net10.0`, no Windows APIs) holds every rule and check: log tracking, the loopback collector on `127.0.0.1:16493`, client settings and the PowerShell status line bridge, presentation, the runner and the updater. `TokenCat.App` (`net10.0-windows`) is the thin shell: tray icon, flyout dashboard, Settings window, system sampler, login item (`HKCU\…\Run`) and the command-line flags. `TokenCat.Checks` is a console runner for the Core suites.
- **Shared with the Mac**: the version is read from `build.sh` through `Directory.Build.props`, and the sprites and manifest are embedded from `Assets/`, so both apps carry one version and one set of art. Settings use the Mac's UserDefaults key names in `%LOCALAPPDATA%\TokenCat\settings.json`.
- **Client folders**: the same registry with Windows locations. Home-folder clients use `%USERPROFILE%` (`.codex`, `.claude`, `.cursor`, `.grok`, `.openclaw`, `.kimi-code`, `.kimi` and the rest), and `CODEX_HOME`, `CLAUDE_CONFIG_DIR` and the other variables above move them the same way; the OpenCode family and Amp use `%USERPROFILE%\.local\share` (or `XDG_DATA_HOME`). Elsewhere: Cline-family tasks in every `%APPDATA%\<editor>\User\globalStorage\<extension>\tasks`, Qoder's `%APPDATA%\Qoder\SharedClientCache\cli\projects`, Cursor's database `%APPDATA%\Cursor\User\globalStorage\state.vscdb`, Hermes in `%LOCALAPPDATA%\hermes` (or `HERMES_HOME`), Goose in `%APPDATA%\Block\goose\data\sessions` (or `GOOSE_PATH_ROOT`) and Kimi Work in `%APPDATA%\kimi-desktop\daimon-share\daimon\runtime\kimi-code\home\sessions`. Gemini CLI's macOS sandbox folder and omp's `XDG_DATA_HOME` layout have no Windows counterpart.
- **On-screen widget** (0.12.0): the menu bar item, drawn by the same rules (items, fixed cell widths, state marks, label tones) in a small borderless, topmost window that never takes the focus and stays out of the taskbar and Alt+Tab. At 100 % one point is a whole number of pixels at every display scale, so the character stays crisp; larger sizes (up to 300 %, `widgetScale`) keep it crisp at whole pixels and draw it smoothly in between. It shares the tray animator's frame timer, checks for a full-screen app (`SHQueryUserNotificationState`) on the 1-second update, and keeps one position per monitor setup (`widgetPositions`); a resize keeps the nearest screen edges in place. Settings › Widget is the Mac's Menu Bar pane (`showWidget`, `statusBarLayout`, `metricOrder`, `visibleMetrics`) plus the size, which its right-click menu and Ctrl + mouse wheel also change; the widget's character (`showRunner`) is the `Character` checkbox at the top of its item list, as on the Mac.
- **Checks parity**: each Core suite is a 1:1 port of a Swift check suite with the same failure descriptions, run in Korean as on the Mac, so a mismatch can be found in both trees with one search. Core builds and its checks run on macOS too (`dotnet build windows/TokenCat.Windows.slnx -c Release`, `dotnet run --project windows/TokenCat.Checks -c Release`). On Windows, `TokenCat.exe --self-test` adds the App checks (embedded art, icon handle leaks, theme contrast).
- **CI** ([`windows.yml`](../.github/workflows/windows.yml)): on pushes to main and pull requests that touch `windows/`, `Assets/` or `build.sh`, a `windows-latest` runner builds with warnings as errors, publishes the single-file `TokenCat.exe` (win-x64, self-contained), checks that its ProductVersion equals the `build.sh` version, then runs `--self-test` (the App checks and the Core suites), `--telemetry-lifecycle-checks` (real loopback, plus the bridge command through Git Bash and PowerShell), `--update-selftest` on the zip it just packed and `--snapshot`, and uploads the zip and snapshots as artifacts.
- **Release** ([`release.yml`](../.github/workflows/release.yml)): a `windows` job on `windows-latest` repeats the build, `--self-test` and version check, packs `TokenCat-Windows.zip` (`TokenCat.exe` and `LICENSE` as flat entries), runs `--update-selftest` on it, `--telemetry-lifecycle-checks` and `--snapshot`, and hands it to the Mac release job. That job verifies its SHA-256, attaches it to the same draft as `TokenCat.zip`, publishes only when both assets' `digest` values match, and reads both back from `/releases/latest`. The release notes have a Windows install section in English and Korean. The exe must be built on Windows, because only there does the SDK write the version resource the updater compares with the tag, and a failing Windows build blocks the whole release.
- **Updater**: the same `/releases/latest` request; the Windows app installs only `TokenCat-Windows.zip`. It checks the size and SHA-256, accepts only `TokenCat.exe` and `LICENSE` in the zip, compares the new exe's ProductVersion with the release, renames the running `TokenCat.exe` to `TokenCat.exe.old`, moves the new one in and relaunches with `--after-update`. The Mac app still looks only for `TokenCat.zip`.
- **Not covered by CI**: the tray at each display scale, SmartScreen and Smart App Control, the bridge under an IDE or the desktop app, and an in-app update between two real releases are on the PC checklist (DESIGN.md §12).

```sh
dist/TokenCat.app/Contents/MacOS/TokenCat --self-test
dist/TokenCat.app/Contents/MacOS/TokenCat --diagnose
dist/TokenCat.app/Contents/MacOS/TokenCat --connect-telemetry
dist/TokenCat.app/Contents/MacOS/TokenCat --telemetry-readings
dist/TokenCat.app/Contents/MacOS/TokenCat --disconnect-telemetry
dist/TokenCat.app/Contents/MacOS/TokenCat --live-check
dist/TokenCat.app/Contents/MacOS/TokenCat --snapshot work/dashboard.png
dist/TokenCat.app/Contents/MacOS/TokenCat --snapshot work/dashboard-light.png --light
dist/TokenCat.app/Contents/MacOS/TokenCat --snapshot-fixtures work/fixtures
dist/TokenCat.app/Contents/MacOS/TokenCat --snapshot-menubar work/menubar.png
dist/TokenCat.app/Contents/MacOS/TokenCat --snapshot-menubar work/menubar-states.png --fixtures
dist/TokenCat.app/Contents/MacOS/TokenCat --snapshot-settings work/settings.png --pane all
dist/TokenCat.app/Contents/MacOS/TokenCat --telemetry-lifecycle-checks
dist/TokenCat.app/Contents/MacOS/TokenCat --notification-status
dist/TokenCat.app/Contents/MacOS/TokenCat --update-check
dist/TokenCat.app/Contents/MacOS/TokenCat --live-limits
```

`--diagnose` prints only system values and token and measurement metadata (including full project paths and session titles, for checking on this Mac only). `--telemetry-readings` checks the measurement metadata of the running TokenCat collector. `--snapshot` saves a dashboard image with real local metrics. `--snapshot-fixtures` saves 23 images, dark and light, of dashboard states from synthetic data (input needed, retry, tool categories, waiting for log, quiet, context, subsessions, expanded list, row details, keyboard selection, empty, loading, telemetry warning, Increase Contrast, a Claude Code-only screen, and the update line's new version, downloading and failed states) and parts sheets (five first-launch outcomes, and limit rows: seven for Codex, including live reads and an omp record, and four for Claude), without reading local logs, the collector or host information; session titles in them are made up. `--snapshot-menubar <png> [--light] [--inline|--minimal] [--highlighted] [--fixtures] [--no-runner] [--character cat|dog|hamster|penguin|robot]` saves a menu bar preview with the same native renderer. `--fixtures` draws all four columns of light, dark and open states, so `--light` and `--highlighted` apply only to real-data previews; its last four rows turn on the Average speed item (one, two and four measuring clients, then none). `--snapshot-settings <png> [--light] [--pane general|menubar|cat|telemetry|about|all] [--character cat|dog|hamster|penguin|robot] [--fixtures [--update-failure network|translocated|not-writable|no-digest|invalid-bundle] [--setup-note unknown|skipped|recreated] [--login requires-approval|enabled] [--notifications denied|authorized]]` renders Settings tabs off screen (`--notifications denied` also turns on every notification choice to make the longest state) and reports each tab's height (flagged when over 600 pt). `--telemetry-lifecycle-checks [port]` tests collector start, telling port users apart, retries and `Retry Now` on a real loopback port, so it's kept separate from the default `--self-test`. `--notification-status` only reads the notification permission state without asking for it. `--update-check` reads the latest release with one GET and prints the comparison with the current version, without downloading, installing or opening any window. `--live-limits` runs one [live usage limit check](#live-usage-limits) per provider (so it contacts OpenAI through the Codex CLI and Anthropic) and prints only the numbers, never the token. The first CPU and network samples have no previous counters, so they're unmeasured; values show from the second sample. Add `--language en` or `--language ko` to any of these to pick the output language.

With `--fixtures`, `--snapshot-settings` also takes `--collector listening` (a healthy collector instead of the port conflict), `--telemetry-disconnected` (the Telemetry tab after `Disconnect…`) and `--layout minimal|compact|inline` (the Menu Bar tab under that layout, its item rows dimmed under Minimal).

`--self-test` checks, without the network, log duplicates, partial records, time boundaries, resumed sessions, separating multiple sessions, model changes, subagent paths, turn ends, input needed, retries, limits, context and more; runner manifest v3, frame counts per pose, timing, the effects layer, pixel heads and 0/255 alpha; OTLP parsing, identifier linking and speed computation; limit parsing from the Claude status line JSON and the Claude desktop app's usage history; display states, groups, the `Speed now` and speed column rules, menu bar widths and settings migration; settings preservation, backup, restore (only TokenCat entries in modified files), conflicts, partial save failures and the status line bridge (wrapping, the original command file, adding to an earlier connection, restoring only the status line); and updates (version comparison, release parsing, digest, rate limits and retry intervals, install conditions, and unzipping, bundle verification and replacement using a copy of this app); and language choice, English texts and time formats. The checks run in Korean and switch language where they check English texts, so they don't depend on `--language`.

`--live-check` collects the real system and local logs for about 6 seconds at the automatic refresh interval. It prints the refresh interval, duplicate start prevention and blocking of refreshes after quit as JSON, and returns exit code 1 on failure. It doesn't call any model.

The build is an ad-hoc signed universal app. App Store distribution, Developer ID signing and notarization aren't included, and for updates only the check is automatic; installing happens only when you click ([Updates and distribution](#updates-and-distribution)).
